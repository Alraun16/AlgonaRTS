# ADR — Архитектура Presentation

**Статус:** принято  
**Актуально на:** `cc83044`  
**Область:** отображение массовых боевых Unit

## Контекст

Проект — RTS на UE 5.8 с расчётом минимум на 20 000 боевых сущностей.  
Simulation должна оставаться независимой от способа отображения, а Presentation — заменяемой без изменения Simulation Core.

## Принятые решения

- **Simulation ≠ Presentation.** Simulation хранит авторитетное состояние Unit. Presentation только получает снимки состояния и отображает их.
- **Без Actor-per-Unit.** Основной путь отображения использует `UInstancedSkinnedMeshComponent`.
- **Simulation работает фиксированно на 40 Гц.** Между снимками Presentation сглаживает движение на GPU через `PreviousTransform → CurrentTransform`.
- **GPU-интерполяция оставляется полной для представленных Unit.** A/B-тест не показал измеримой выгоды от её отключения, поэтому дополнительные уровни качества интерполяции сейчас не вводятся.
- **Presentation работает только с видимым рабочим набором Unit.** Полный набор армии не передаётся в рендер каждый кадр.
- **Предварительный отсев — через Unit spatial grid.** Размер ячейки — 100 м.
- **Точный отсев Perspective — через закэшированную `ViewProjectionMatrix` и `ViewRect`.** `ProjectWorldLocationToScreen` для каждого Unit не используется.
- **На близком зуме используется адаптивный запас отсечения**, чтобы Unit не исчезал у края экрана до полного выхода модели.
- **Выгрузка снимков состояния** читает плоские массивы состояния Unit в Simulation напрямую по `UnitId` (P2, шаг 6a). Прежняя гибридная схема «`< 6%` — прямой доступ к Mass, `>= 6%` — проход Mass с маской» удалена вместе с хранением Transform в Mass.
- **Сортировка `UnitId` перед экспортом запрещена.** Она дала заметную лишнюю стоимость и не нужна для корректности.
- **Порядок Unit из spatial grid не считается стабильным.** Presentation не должна зависеть от порядка возвращённых `EntityId`.
- **Изменение видимого набора обновляется инкрементально.** Существующие `InstanceId` сохраняются, вышедшие Unit удаляются, новые добавляются. Полный `RebuildInstances()` оставлен только как запасной путь.
- **Анимация «идёт / стоит» выбирается в Presentation по наблюдаемой скорости Unit (2026-10-14).** У инстанса `UInstancedSkinnedMeshComponent` ровно одно анимационное число — номер последовательности банка анимаций. 0 — ходьба, 1 — покой; без второй последовательности в банке все Unit, как раньше, идут.
  - Покой задаётся в ассете банка: вторая последовательность с `PlayRate 0`, у которой поза стойки — **первый кадр** клипа (или своя Idle-анимация). При создании провайдера анимаций из банка (`UAnimSequenceTransformProviderData::CreateFromAnimBank`) движок переносит только `Sequence`, `PlayRate` и `Position`, поэтому флаги `AutoStart` и `Looping` на этом пути ни на что не влияют.
  - **`Position` при `PlayRate 0` не работает** (проверено в редакторе и по коду, 2026-10-14). Провайдер считает время дорожки как `(t − метка) × PlayRate`, а метку получает как `t − Position / PlayRate`; при нулевой скорости деление пропускается и метка равна `t`, так что время всегда 0 — кадр 0. Формула `Position += PlayRate × dt` из самого банка анимаций (`FAnimBankTrackPackedData`) к этому пути не относится. Штатный застывший кадр — ручные дорожки провайдера (`SetManualData`), но они есть только у экземпляра провайдера на компонент (`UAnimSequenceTransformProviderDataInstance`), а отображение подключает провайдер-ассет напрямую; переделка ради позы стойки отклонена.
  - Время дорожки в банке общее для всех инстансов одного номера: все стоящие Unit в одной позе, как вся армия шагает в такт.
  - Скорость — уже считаемая для уровней интерполяции `ObservedLinearSpeedsCmPerSecond` (смещение между снимками). Simulation и снимок Unit не меняются: Presentation по-прежнему знает только то, что видит.
  - Гистерезис: идёт выше 60 см/с, стоит ниже 30 — переминающийся в толкучке Unit не мигает между позами. Прошлое состояние для гистерезиса хранит сам компонент (`GetInstanceAnimationIndex`), поэтому отдельный массив, который пришлось бы переносить при каждой смене видимого набора, не нужен. Номер меняется (`SetInstanceAnimationIndex`) только на переходе.

## Последствия

Плюсы:
- Presentation масштабируется независимо от общего количества сущностей;
- Simulation не зависит от камеры, рендера и конкретного способа визуализации;
- смена порядка Unit в spatial grid не вызывает полную пересборку инстансов;
- архитектура остаётся пригодной для multiplayer и дальнейшей замены Presentation.

Ограничения / технический долг:
- материалы GPU-интерполяции — обычные сохранённые ассеты в `/Game/Algona/Presentation/GpuInterpolation`:
  - их один раз генерирует редакторский модуль `AlgonaRTSEditor` командой `algona.P1.BuildGpuInterpolationMaterials`;
  - игра (PIE и Standalone) только загружает готовый Material Instance, без `MaterialEditor`;
  - прежний рантайм-путь через `UMaterialEditingLibrary` падал в Standalone и удалён;
  - после изменения исходных материалов меша или раскладки custom data ассеты нужно удалить и сгенерировать заново;
  - Material Instance переносит только uniform-параметры исходного слота, как и прежний путь (static switch не переносятся);
- **«Пол» движка и редактора по FPS.**
  - Замер (PIE, Ryzen 9 7950X + RTX 4090): при `algona.P1.Presentation 0` и `algona.P0.UnitCount 10` около 200 FPS — примерно столько же, сколько с Presentation на 100 000 Unit.
  - Кадр упирается в Game thread, а не в GPU; значительная часть этого времени не относится к Simulation и Presentation.
  - **Перед оптимизацией FPS сначала измерить этот «пол»** (в Standalone или собранной игре, через Unreal Insights), иначе можно оптимизировать не то.
- текущий адаптивный запас отсечения использует эталонную высоту Unit 170 см; при разных типах существ надо перейти к реальным bounds соответствующего типа отображения.
