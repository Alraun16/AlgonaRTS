# ADR — Архитектура движения Unit и структуры Squad (P2)

**Статус:** принято, уточняется по шагам  
**Актуально на:** `cc83044`  
**Область:** движение Unit к слотам, хранение слотов Squad, локальное избегание

> ADR (Architecture Decision Record) — короткая запись «контекст → решение → последствия», чтобы не обсуждать уже принятое заново.

## Контекст

- Целевой стресс-тест — 100 000 Unit, каждый Unit потенциально подвижен.
- Simulation работает фиксированным шагом 40 Гц: на весь шаг есть 25 мс, и в них позже должны поместиться бой, AI и прочие системы.
- Мультиплеер — server-authoritative: сервер считает, клиенты получают результат.
- Игровые правила движения и отрядов описаны в ГД-документе «Алгоритм движения и отрядов» (вне репозитория). Часть его устарела — см. раздел ниже.

### Эксперимент со штатным Mass Avoidance (отклонён)

- Функционально удался: `UMassMovingAvoidanceProcessor` можно вызывать вручную ровно один раз на наш fixed step, без зависимости от FPS и без изменения Transform за спиной Simulation (проверено на 64 сущностях).
- По производительности провалился: на 100 000 Unit — около 0.5–0.9 FPS, Game Thread около 1200 мс, GPU 3–4 мс.
- Разбивку по стадиям (очистка сил, hash-сетка препятствий, сам processor) не измерили, но разрыв с бюджетом слишком велик.
- **Решение:** штатный Mass Avoidance не используется. Экспериментальный код в рабочую ветку не переносится.

## Принятые решения

### 1. Три уровня движения

| Уровень | Что решает | Сложность |
|---|---|---|
| **L1. Squad** | путь, скорость центра, поворот, разворот, Reform, назначение слотов | O(число Squad) |
| **L2. Steering к слоту** | желаемая скорость Unit: скорость слота + поправка к слоту + торможение у цели | O(N), без соседей |
| **L3. Локальное избегание** | Unit не проходят друг сквозь друга | O(N × соседи) |

- **Поворот и разворот строя — ответственность L1, а не L3.** Большинство пересечений внутри Squad создаёт сама логика слотов. Их дешевле предотвращать, чем разруливать через avoidance.

### 2. L3 — вариант E: расталкивание с отбором по перекрытию Squad

- **Базовый механизм (B):** если два Unit перекрываются, каждый сдвигается от другого (separation).
  - Соседей ищем через мелкую сетку, которая перестраивается каждый тик.
  - Используется Jacobi-схема: все Unit читают позиции прошлого шага и пишут только свою поправку. Результат не зависит от порядка обхода и числа потоков.
  - Сдвиг за тик ограничен. Стоящий Unit держит место надёжнее движущегося (уступает 1/3 сдвига; пересмотрено 2026-09-22, раньше было наоборот) и после толчка возвращается в слот через L2.
- **Отбор (E, broadphase):** broadphase — дешёвая грубая предварительная проверка. Сначала по фактическим границам Unit каждого Squad находятся пересекающиеся пары Squad; в сетку и расталкивание попадают только их Unit.
- Худший случай («все армии в свалке») сводится к B для всех Unit, поэтому B сам по себе обязан укладываться в бюджет на 100 000.
- Unit в статусе «Потерянный» в расталкивании не участвуют.
- Unit могут иметь разный радиус (кавалерия, тролли). Способ хранения крупных Unit в сетке выбирается на шаге построения сетки.

Отклонены:
- **RVO/ORCA и другие предиктивные методы** (каждый Unit заранее выбирает скорость без столкновений по скоростям соседей) — слишком дорого на 100 000.
- **Flow field** (общее поле направлений движения) — это инструмент глобального пути, а не движения к слоту.
- **Движение без избегания Unit-Unit** — в бою и давке контакты всё равно нужны.

### 3. Хранение слотов Squad

- **Раскладка отделена от назначения.**
  - Раскладка — массив смещений слотов от центра Squad в координатах самого Squad. Генерируется функцией формы только при Reform.
  - Назначение — массив `ActiveUnitIds`, где индекс равен номеру слота.
- **Порядок слотов:** от передней строки к задней, внутри строки от центра к краям, правая сторона первой.
  - Пример: строка из 3 — центр, правый, левый; строка из 4 — правый средний, левый средний, правый крайний, левый крайний.
  - Неполная строка центрируется автоматически.
  - Этот же порядок — очередь при проходе через узкое место: достаточно обходить слоты от 0 до последнего.
- **Генератор формы** — чистая функция `BuildAlgonaFormationLayout` (вход: параметры формы и число слотов; выход: слоты, число строк, радиус, X передней строки).
  - Формы различаются правилом «сколько слотов в строке» (`switch` по форме, без иерархии классов).
  - Расстояния задаются двумя параметрами: между слотами в строке (`SlotSpacing`) и между строками (`RowSpacing`).
- **Оси в коде — конвенция UE:** X — вперёд по направлению Squad, Y — вправо. В ГД-документе оси названы наоборот.
- **Изменения состава:**
  - смерть активного Unit — на его место встаёт последний активный Unit массива (swap-remove);
  - подкрепление — добавляется в конец;
  - зеркальный разворот и будущие режимы ветеранства — перестановка `ActiveUnitIds`.
- Unit хранит `SquadId` и `SlotIndex` во фрагменте. Связь «Squad → Unit» и «Unit → слот» меняется только в функциях Squad (добавить, убрать, Reform, перестановка) и проверяется автотестом.
- **Опорная точка Squad — центр раскладки**, а не центр передней линии.
  - Центр — середина прямоугольника, охватывающего все слоты (bounding box), а не среднее положение слотов. Поэтому он меняется только при появлении или исчезновении целой строки.
  - Радиус Squad (от центра до самого дальнего слота) считается при Reform.
  - **Reform из-за изменения состава** (смерть, Потерянный, возвращение, подкрепление): строки Unit остаются на месте, центр Squad сдвигается к новому геометрическому центру.
  - **Reform по приказу игрока** (длина строки, форма): центр Squad остаётся на месте. Приказы формулируются относительно центра, как и приказ движения.
- Мировая позиция слота = центр Squad + смещение, повёрнутое на направление Squad.
- `FormationRevision` увеличивается при каждом изменении раскладки. Зеркальная таблица строится лениво, когда нужна, и проверяется по этой ревизии.
- Длина строки прямоугольника по умолчанию: 5 при ≤20 Unit, 10 при >20 (временное правило первой реализации).
  - Правило пересчитывается при каждом Reform, пока игрок не задал ширину построения вручную.
  - После ручной установки ширины длина строки сохраняется.
- Типы слотов (битовая маска допустимых типов) и ветеранство в первую реализацию не входят. Структура допускает их добавление без переделки.
- `SquadEntityRanges` (предположение, что Unit одного Squad лежат подряд) удалён: при смерти и подкреплении оно перестаёт быть верным.
  - Спящий путь экспорта по отрядам (`ExportUnitSnapshotsForSquads`, для отключённой Squad Grid) берёт Unit из `ActiveUnitIds`.
- **Проверка связи Squad ↔ Unit:** `ValidateSquadMembership` после создания армии в не-shipping сборках.
  - Проверяет `ActiveUnitIds.Num() == Slots.Num()`, `SquadId`/`SlotIndex` каждого Unit и то, что каждый Unit ровно в одном слоте.
  - При ошибке старт Simulation прерывается.

### 3a. Очередь команд, текущий приказ и Reform

- **Очередь команд — транспорт** от игрока, сети и AI до Simulation.
  - Команды не меняют состояние сразу: они применяются строго по порядку поступления в начале следующего fixed step, затем очередь очищается.
  - Локальный игрок, удалённый игрок и AI идут одним путём; порядок команд воспроизводим; изменения не пересекаются с многопоточными стадиями шага.
  - Одна общая очередь `FAlgonaSquadCommand` с типом команды (`Move`, `SetRowLength`, позже форма и др.), а не массив на тип: порядок между типами сохраняется.
- **Текущий приказ хранит сам Squad.** Новый приказ движения полностью заменяет текущий, включая отложенные действия по прибытии. Цепочки приказов (Shift) в будущем — список внутри Squad, не очередь команд.
- **Операции над составом — функции `FAlgonaSquad`**: `RemoveActiveUnitAt` (swap-remove), `AddActiveUnit`, `RebuildFormationLayout`, `ReformAfterCompositionChange`, `ApplyRowLengthOrder`.
  - Они меняют только массивы Squad. Вызывающий код обновляет `SlotIndex` во фрагменте переставленного Unit.
  - Удаление и добавление Unit в игре подключаются на шаге Потерянных и в P3 (смерть); до этого они проверяются автотестами.
- Длина строки по приказу ограничена диапазоном 1…100 (`AlgonaFormationLimits`).
- Приказ длины строки на Reform по составу не влияет: после ручной установки правило 5/10 больше не применяется.

### 4. Конвейер движения и многопоточность

- Каждый тик движение идёт так: собрать данные Unit из Mass в плоские массивы → посчитать L2/L3 → записать результат обратно в Mass и Unit Grid.
- Формат массивов — SoA (Structure of Arrays): отдельный массив на каждое поле. Массивы переиспользуются между тиками.
- **Цель по железу:** 4 ядра. На 8/12/16 ядрах многопоточные стадии должны ускоряться примерно пропорционально.
  - Каждый поток пишет только свои элементы, общих записей нет.
  - Однопоточные остатки (сбор, запись, агрегация по Squad) измеряются отдельно, потому что именно они ограничивают выигрыш.
- Таймеры и счётчики Simulation — в тиках, а не в секундах (5 с = 200 тиков).
- SimLOD, если понадобится, опирается только на состояние Simulation, никогда на камеру.

### 4a. Многопоточность конвейера движения (шаг 6)

- **Правило:** каждая задача пишет только в элементы своих Unit; Squad, раскладки и Unit Grid в это время только читаются. Результат одинаков при любом числе потоков.
- **gather и scatter** — `FMassEntityQuery::ParallelForEachEntityChunk` (чанки Mass раздаются потокам).
  - Флаг `Force`: режим задаёт наш переключатель, а не глобальная настройка `mass.AllowQueryParallelFor`.
  - `SetParallelCommandBufferEnabled(false)`: конвейер не отправляет команды Mass, буферы команд не нужны.
- **steer** — `ParallelFor` по Unit, минимальная порция 1024 Unit.
- **Unit Grid** (`TMap` внутри) не изменяется из нескольких потоков: параллельный scatter только помечает Unit, перешедшие в другую ячейку (`NeedsCellUpdate`), а сетка обновляется последующим последовательным проходом.
- **Переключатель `algona.P2.ParallelMovement`** (1 — рабочие потоки, 0 — один поток) остаётся в проекте постоянно: для A/B-замеров и для исключения ошибок многопоточности.
- **Замер «целевой машины»:** Standalone с параметром запуска `-corelimit=4`. В строке `[P2 Metrics]` выводятся `parallel` и `workers` (число рабочих потоков движка).

### 4b. Хранение состояния Unit в плоских массивах (шаг 6a, пересмотр P0)

- **Решение:** источник истины для «горячих» данных Unit — плоские массивы Simulation Subsystem (`FAlgonaUnitStateArrays`, индекс = `UnitId - 1`): позиция, поворот, скорость, `SquadId`, `SlotIndex`.
- **Mass-сущность Unit** хранит только идентичность: `FAlgonaUnitIdFragment` и тег. Фрагменты Transform, SquadMember и Movement удалены. У каждого поля ровно один хозяин.
- **Почему:** почти все потребители обращаются к Unit по номеру (L3 — к соседям, бой P3, экспорт Presentation), а порядок чанков Mass не совпадает ни с одним из этих способов доступа. Копирование gather/scatter (~1.5 мс из ~2.4 на 4 ядрах) убрано.
- **Конвейер:** `SteerUnits` (параллельно, помечает смену ячейки Unit Grid) → `UpdateUnitGrid` (последовательно).
- **Экспорт снимков Presentation** читает массивы напрямую по `UnitId`. Гибридная схема «<6% прямой доступ / ≥6% проход Mass» из baseline P0 больше не нужна и удалена.
- **Рассмотренные альтернативы:** оставить gather/scatter; считать L2 прямо в чанках Mass (L3 и бою всё равно нужен доступ по номеру); полный отказ от Mass (решается перед P3, когда станет ясно, какие данные Unit «холодные»); массивы + копия в Mass по требованию (нет внешних потребителей Transform).
- **Открыто для P3:** смерть и появление Unit (дыры в номерах, переиспользование `UnitId`), нужен ли Mass для Unit вообще.

### 4c. L2 — движение Unit к слоту и поворот Unit

- **Конвейер за тик:** `GatherUnitMovementState` (сбор из Mass) → `SteerUnits` (L2) → `ScatterUnitMovementState` (запись в Mass и Unit Grid). Метрики показывают каждую стадию.
- **L2 — управление скоростью, а не перенос на слот.** Желаемая скорость = скорость слота (упреждение, пока равна скорости центра Squad) + поправка к слоту.
  - Отставание считается от положения слота в начале тика: центр Squad в этом тике уже сдвинут.
  - Скорость поправки ограничена максимальной скоростью Unit, скоростью торможения с замедлением `ArrivalDeceleration` (800 см/с²) и расстоянием до слота за один тик (без перелёта).
  - Итоговая скорость не больше максимальной скорости Unit.
  - Так расталкивание L3 позже просто добавится к движению, а не будет стираться «прыжком» на слот.
- **Максимальная скорость Unit** = заданная скорость Squad × `UnitSpeedFactor` (1.25 по умолчанию, параметр Squad; окончательная настройка — на шаге статусов отставания).
  - «Заданная» — скорость ходьбы или бега с учётом замедления, а не мгновенная скорость центра: иначе у стоящего Squad Unit не дошли бы до слотов.
- **Поворот Unit** хранится во фрагменте (`FacingYawRadians`), Transform строится из него.
  - Дальше 1 м от слота и в движении — по ходу движения; в слоте или рядом — по направлению Squad.
  - Поворот плавный, не быстрее 360°/с (было 540°/с — разворот выглядел мгновенным, 2026-09-17).
  - Анимации шага вбок могут изменить правило позже (маловероятно).
- **Желаемая и фактическая скорость хранятся раздельно**: ограничение ускорения (шаг 10) станет стадией между ними.
- Чистые функции L2 (`AlgonaUnitSteering`) покрыты автотестами.

### 4c-bis. Назначение слотов при Reform (2026-09-26)

- **Проблема:** раскладка при Reform менялась, а назначение Unit по слотам — нет. Unit с дальнего края мог получить слот на противоположном краю и бежал через весь строй.
- **Два этапа (2026-09-27):** сначала структура — слоты раздаются по порядку раскладки (ряды спереди назад, внутри ряда от центра к краям), и первыми их получают самые крупные Unit, поэтому крупные встают в первую строку по центру и строй симметричен. Затем расстояние — внутри группы одного размера работает разбиение по рядам. Побочный выигрыш: какие слоты достанутся крупным, известно заранее, и предпросмотр приказа показывает круги верного размера в верных местах.
  - Когда в P3 появятся типы существ, тот же механизм расширится до ролей: вместо «сначала крупные» будет «сначала щитоносцы, потом пехота, потом лучники». Отдельные функции построения на каждый отряд не нужны — нужен только порядок приоритета.
- **Решение — разбиение по рядам:** Unit сортируются по глубине в системе координат Squad, передний ряд забирает столько передних Unit, сколько в нём слотов, следующий — своих, и так до конца; внутри ряда Unit сортируются слева направо и раскладываются по слотам ряда. O(n log n), взаимное расположение сохраняется — длинных перебежек через строй не бывает.
- Отклонены: венгерский алгоритм (математический минимум пути, но O(n³) и сложный код ради разницы, незаметной на глаз) и жадный перебор пар (оставляет одному Unit длинную пробежку, как было с зеркальной таблицей).
- Вызывается при Reform, меняющем раскладку (приказ ширины строя, смена состава). Порядок слотов как очереди при проходе узких мест при этом меняется — это допустимо.
- Чистая функция `BuildAlgonaSlotAssignmentByPosition`, автотест `Algona.P2.Formation.SlotAssignment`.

### 4d. L1 — поворот и разворот Squad (шаги 8–9, 2026-09-17)

- **Поворот строя** — вращение направления «вперёд» вокруг центра Squad не быстрее максимальной угловой скорости. Слоты идут по дуге, Unit следуют за ними через L2.
- **Максимальная угловая скорость** = `TurnSpeedFactor` × заданная скорость Squad / радиус раскладки. `TurnSpeedFactor` = 1.0 (параметр Squad): крайний слот не быстрее Squad, у крайних Unit остаётся запас `UnitSpeedFactor` (1.25) на догон. В ГД было 1.25 — отклонено, иначе у крайних Unit нет запаса. Считается на лету, поэтому сразу учитывает Reform и будущую смену скорости ходьбы/бега.
- **Совмещение движения и поворота:** оба идут одновременно с полной скоростью. Деление `0.5 / 0.5` из ГД было реализовано и отклонено после запуска — движение выглядело неестественно замедленным. Также отклонены: бюджет по скорости крайнего Unit и «как машина» (путь центра становится дугой — конфликт с путями навигации).
- **Бюджет скорости крайнего слота:** на ходу скорость центра и скорость от вращения складываются, и крайние Unit бежали в 2–3 раза быстрее остальных. Поэтому угловая скорость ограничена так, чтобы суммарная скорость крайнего слота не превышала `MaxSlotSpeedFactor` (1.3) от скорости Squad, но не падала ниже `MinTurnRateFactor` (0.4) от максимальной угловой скорости. Стоящий Squad поворачивается с полной угловой скоростью.
- **L2 учитывает вращение:** скорость слота = скорость центра + `YawRate` × (X × Right − Y × Forward). `YawRate` Squad за тик хранится как `CenterVelocity`.
- **Режим движения** решается при получении приказа по длине пути (границы подобраны в редакторе: исходно 8 и 16 м от интервала строя, после проверки 10 и 20 м; марш к тому же не раньше двух радиусов раскладки). Границы подбираются в запущенной игре через CVar `algona.P2.SidestepMaxDistance` и `algona.P2.FaceMovementMaxDistance` — новое значение действует со следующего приказа:
  - **до 10 м:** Squad сохраняет конечное направление, Unit смотрят по направлению Squad — шаг вбок или назад;
  - **10–20 м:** Squad сохраняет конечное направление, но Unit смотрят по направлению движения. Режим добавлен после проверки: «лунный бег» боком на десяток метров выглядел странно (2026-09-20);
  - **дальше:** марш — Squad смотрит по ходу движения и начинает доворот к конечному направлению на подходе (путь доворота = скорость × угол / угловая скорость × `FinalTurnDistanceFactor` 0.8).
  - После прибытия центра незаконченный поворот продолжается на полной скорости.
- **Разворот больше 135°** — мгновенно, отражением самой раскладки: у всех слотов меняется знак смещения, направление Squad меняется на противоположное, номера слотов приводятся к обычному порядку. Положения слотов в мире не меняются, поэтому **ни один Unit не двигается** — Unit только разворачиваются на месте. Остаток (меньше 90°) — обычным поворотом.
  - Порог именно 135°, а не 90°: зеркальный разворот мгновенный, поэтому по углу выигрывает уже с 91°, но тогда поворот на 110° выглядел так, будто Squad сначала отворачивается от цели и доворачивает в обратную сторону (проверка в редакторе, 2026-09-20). С 135° зеркало остаётся только для разворотов назад.
  - После отражения слоты переназначаются тем же правилом, что при Reform: первая строка теперь с другой стороны, поэтому крупные Unit переходят в неё, а их прежние места занимают ближайшие мелкие. Для однородного Squad назначение получается тождественным, и никто не двигается.
  - Неполная строка после отражения оказывается передней. Это принято сознательно: следующий Reform вернёт её назад.
  - Отклонено: зеркальная таблица слотов из ГД (перестановка Unit по ближайшим зеркальным слотам). Была реализована и отклонена 2026-09-18: при неполной строке точного отражения нет, и часть Unit меняла места, вплоть до пробежки через весь отряд. Варианты «оптимальное сопоставление» и «симметричная раскладка» не понадобились.
  - После разворота — плавный старт `MirrorTurnStartSeconds` (0.5 с — столько же занимает разворот Unit): скорость движения и поворота Squad растёт от нуля до полной. Вариант с полной остановкой Squad на это время был реализован и отклонён после запуска (2026-09-17).
- **Точка приказа** выбранных Squad показывается кружком со стрелками, пока Squad идёт: рисуется в `AAlgonaHUD` по спроецированным мировым точкам, размер привязан к кругу выбора Unit.
- **Скорость Unit:** `UnitSpeedFactor` = 1.02 (460 см/с при скорости Squad 450). Запас на догон почти нулевой: отставший догоняет, когда Squad сам сбавляет ход в давке, а не улетает вперёд. Бюджет крайнего слота (`MaxSlotSpeedFactor`) опущен до 1.0, иначе слот на повороте был бы недосягаем. Подбор на ходу — CVar `algona.P2.UnitMaxSpeed`. Раньше было 1.3 и 1.5 на повороте. На ходу крайний слот при повороте движется со скоростью центра плюс скорость от вращения (до 2 скоростей Squad), и с 1.25 Unit заметно отставали (проверка в редакторе, 2026-09-17).
- **Скорость Squad** `CenterMoveSpeed` = 450 см/с (было 300 — слишком медленно на глаз). Для подбора в запущенной игре есть CVar `algona.P2.SquadMoveSpeed` (0 — не подменять). Раздельные скорости ходьбы и бега появятся вместе с соответствующими приказами.
- **Инерции поворота нет** — угловая скорость сразу максимальная; разгон и торможение поворота добавляются на шаге 10 вместе с инерцией движения.

### 4e. Инерция (шаг 10, 2026-09-20)

- **Центр Squad:** скорость вдоль пути меняется с ускорением `CenterMoveSpeed / AccelerationSeconds` (1.0 с до полной скорости); торможение такое же (`DecelerationFactor` = 1; множитель оставлен для настройки). Желаемая скорость дополнительно ограничена «скоростью подхода» sqrt(2 a s), поэтому центр встаёт ровно в цели без перелёта.
- **Поворот строя:** так же, но для угловой скорости: разгон за ту же 1.0 с до максимальной угловой скорости, ограничение по остатку угла — строй встаёт точно в направлении и не качается.
- **Unit:** фактическая скорость подтягивается к желаемой (результат L2) с ускорением `максимальная скорость Unit / UnitAccelerationSeconds` (0.5 с). Unit разгоняется вдвое быстрее Squad, иначе не догоняет слот. Правило подхода к слоту осталось в желаемой скорости, инерция лежит поверх.
- **Плавный старт после разворота сохранён** как потолок скорости (не второй разгон): пока Unit разворачиваются на месте, потолок поднимается от нуля до полного за `MirrorTurnStartSeconds`; инерция работает под ним. Позже длительность будет браться из анимации разворота Unit.
- Чистые функции `StepValueTowards`, `StepVelocityTowards`, `GetArrivalSpeedLimit` живут в `AlgonaUnitSteering` и покрыты автотестом `Algona.P2.UnitSteering.Inertia` (независимость от длительности тика, остановка ровно в цели).

### 4f. L3 — мелкая сетка соседей (шаг 11, 2026-09-22)

- **Сетка-тор:** таблица корзин — прямоугольник из степеней двойки (всего примерно по числу Unit, на 100k это 512 × 256), клетка мира (X, Y) попадает в корзину (X mod 512, Y mod 256). Память зависит только от числа Unit, а не от размера карты. Совпадают только клетки, отстоящие ровно на ширину или высоту тора (768 × 384 м при клетке 150 см) — вызывающий код всё равно проверяет настоящее расстояние.
  - Свёртка вместо перемешивающего хеша: соседние клетки мира остаются соседними корзинами, поэтому раскладка и поиск соседей идут по соседним местам памяти. С перемешивающим хешем раскладка стоила ~0.22 мс из-за промахов кэша.
  - Отклонено: плотный массив клеток по прямоугольнику, охватывающему всех Unit. Армии в разных концах карты дают огромный и почти пустой прямоугольник (2×2 км при клетке 150 см — 1.8 млн клеток на обнуление каждый тик).
- **Клетка 150 см** (интервал строя). Радиус взаимодействия двух обычных Unit (70 см) меньше клетки, поэтому соседей ищем в 3×3 клетках; корзина, в которую попали две из девяти клеток, обходится один раз.
- **Построение — сортировка подсчётом**, каждый тик заново: корзина каждого Unit (в несколько потоков) → счёт по корзинам → префиксные суммы → раскладка номеров по порядку входного списка (три последних прохода в одном потоке). Раскладка по порядку сразу даёт номера внутри корзины по возрастанию, поэтому обход соседей одинаков при любом числе потоков.
  - Первый вариант (атомарный счёт и раскладка в 30 потоках, таблица вдвое больше числа Unit, отдельная сортировка корзин) занимал ~1.2 мс: атомарные операции дрались за кэш, а проход по корзинам тормозили проверки границ `TArray` в конфигурации Development. Отсюда правило: в горячих циклах обходить массивы через указатели.
- **Вход — список Unit.** Пока это все Unit; на шаге 14 (broadphase) туда пойдут только Unit пересекающихся Squad. Сетка при этом одна общая: группы пересечений в разных частях карты просто лежат в разных клетках.
- **Крупные Unit** (шаг 15) записываются во все клетки, которые накрывают телом. Поиск для обычного Unit не меняется: он по-прежнему смотрит 3×3 вокруг себя и находит крупного в накрытых клетках. Повторная встреча того же крупного в нескольких клетках отсекается при расталкивании.
- Стадия `l3grid` в `[P2 Metrics]`; CVar `algona.P2.LocalAvoidanceGrid 0` выключает перестройку для сравнительных замеров.
- **Замер (100 000 Unit, стресс-сценарий, все потоки):** `l3grid` ~0.25–0.28 мс, весь шаг ~0.9–0.97 мс. По проходам: корзины (в несколько потоков) ~0.07, счёт ~0.04, префиксные суммы ~0.06, раскладка ~0.09.
  - Путь оптимизации: первый вариант ~1.2 мс → указатели, без атомиков и сортировки корзин ~0.40 → свёртка вместо хеша ~0.26.
  - Три последних прохода однопоточные и почти упёрлись в скорость памяти; дальше их имеет смысл трогать, только если после шага 12 (поиск соседей и расталкивание) сетка окажется заметной частью L3.

### 4g. L3 — обход, контакт и теснота (шаги 12–13, 2026-09-22)

- **Шаги 12 и 13 объединены:** схема Якоби сразу устроена под потоки, однопоточный режим для сравнения — `algona.P2.ParallelMovement 0`.
- **Первая версия отклонена после проверки:** чистое расталкивание (толчок при контакте плюс уход вправо в зоне 75 см) механически работало, но выглядело как «упругие шарики»: реакция начиналась за десятую долю секунды до встречи, Unit не тормозили, ехали боком, а жёсткий слот возвращал их за полсекунды. Люди почти не допускают столкновений — они заранее меняют курс и скорость.
- **Две части скорости Unit:**
  - *намерение* — L2 к слоту, обход соседей (позже и хаотичность траекторий) — идёт через инерцию, поэтому курс меняется по дуге;
  - *контакт* — расталкивание реально перекрывшихся — добавляется поверх инерции и действует сразу, как страховка от прохода насквозь.
- **Обход по времени до столкновения (TTC):** движущийся Unit смотрит на соседей впереди в 5×5 клетках (300 см) и считает, через сколько секунд сблизится с каждым до суммы радиусов плюс личного пространства (`AvoidancePersonalSpace` 5 см), если оба сохранят скорость. Реакция растёт по мере сокращения этого времени в пределах `AvoidanceHorizon` (0.8 с).
- **Выбор щели вместо стороны (2026-09-26, замена правила «всегда вправо»):** Unit откладывает опасных соседей на поперечную ось — линию поперёк своего хода — отрезками, которые они займут к моменту наибольшего сближения, и сам стоит в нуле этой оси. Если ноль занят, Unit ищет ближайший свободный сдвиг (края занятых отрезков) и смещается к нему на свою долю к моменту встречи. Стороны получаются разными сами собой: кто чуть левее встречного — уходит влево, кто правее — вправо, поэтому строй расходится «гребёнкой», а не сносится целиком.
  - При точной симметрии сторону решает место Unit в строю: левая половина ряда уходит влево, правая вправо — строй раскрывается и обтекает с двух сторон. Признак разный у соседей по ряду, поэтому запора не возникает.
  - Правило «всегда вправо от своего хода» отклонено после проверки: оно ломает натуральность — при встрече строёв весь передний ряд уходил в одну сторону.
- **Правила встреч:**
  - *встречный* (направления расходятся больше чем на 120°) и *стоящий на пути* — обойти вправо от своего хода, чуть притормозив; встречные уходят в разные стороны и не упираются друг в друга;
  - *попутный впереди* (меньше 60°) — притормозить и идти следом, не обходя; касается и Unit своего Squad при поворотах и перестроениях;
  - *пересекающий* — уступает тот, у кого сосед справа («помеха справа»), второй идёт дальше.
  - Торможение ограничено `AvoidanceMaxBrake` (до 40% скорости), скорость уклонения — `AvoidanceSideRatio` от максимальной скорости Unit. При заметном уклонении Unit поворачивается по ходу, а не идёт боком.
- **Вторая итерация (2026-09-22) после проверки двух встречных отрядов и отряда, идущего на стоящий:**
  - *Отряды не помещались друг в друга по числам:* щель между соседями в строю 150 - 70 = 80 см, а юниту с личным пространством 30 см нужно 100 см. Личное пространство — 5 см (нужно 75 см), ряды проходят «гребёнкой».
  - *Уклонение ровно на недостающее расстояние:* вместо постоянной скорости вбок Unit считает промах — где окажется сосед при наибольшем сближении — и набирает свою долю недостающего до контакта расстояния к моменту встречи. Как только Unit встал напротив щели, угроза пропадает, и он не скользит вдоль всего ряда (раньше весь передний ряд уходил вправо блоком и «стекал» по чужому фронту). Сторона — туда, куда уже смотрит промах; правило «вправо от своего хода» — только для почти точного лобового.
  - *Стоящие расступаются:* стоящий Unit, на которого надвигается идущий, тоже уклоняется — своей долей (1/3), в сторону от пути идущего. Раньше уклонялся только идущий, и стоящий строй был сплошной стеной. Стоящий смотрит только на 3×3 клетки — дешевле, а идущий к этому моменту уже сам уклоняется.
  - *Теснота Squad — только по торможению* (не по обходам), усиление 1.5 вместо 2.5: строй сбавляет ход в настоящей давке, а не при каждом обходе.
- **Третья итерация (2026-09-26) по видео прохода двух Squad:** с личным пространством 5 см Unit проходили друг сквозь друга почти без следа — не хватало всего 5 см, поэтому уклонение было в пару сантиметров, а торможение почти нулевым. Личное пространство — 20 см (нужно 90 см при щели 80), торможение при расхождении — 0.45 и вынесено в CVar, добавлено трение при касании: Unit теряет ход тем сильнее, чем глубже перекрытие, и касание идёт в тесноту Squad. Затор при этом не возвращается: уклонение ограничено недостачей, а расступаются обе стороны.
- **Четвёртая итерация (2026-09-26):** трение по фактической скорости давало дрожание (тормозится каждый тик, тут же разгоняется инерцией), а поворот тела по фактической скорости добавлял шум. Трение переведено в намерение (глубина касания прошлого тика снижает желаемую скорость, дальше инерция), поворот тела считается по намерению.
- **Пятая итерация (2026-09-26):** Unit дрожали в толпе — сторона уклонения выбиралась по промаху, а вплотную промах близок к нулю и его знак скачет каждый тик. Теперь уклонение не считается для уже соприкоснувшихся (их разводит толчок), сторона берётся по промаху только когда сосед явно сбоку (промах больше половины нужного зазора), иначе действует устойчивое правило «вправо от своего хода», и уклонение сглаживается между тиками.
- **Шестая итерация (2026-09-26):** дрожание оказалось обратной связью через собственную скорость: Unit тормозил → время до столкновения росло → угроза пропадала → тормоз отпускался. Время до столкновения теперь считается по намерению Unit (оно не зависит от его же торможения), торможение сглаживается между тиками, у признака «поворачиваюсь по ходу» появился гистерезис.
- **Стоимость обхода (2026-09-30, замер на 4 ядрах).** При массовых столкновениях шаг вырастал до 15–21 мс, из них `steer` 12–17: каждый движущийся Unit просматривал 5×5 клеток и считал время до столкновения для ~25 кандидатов. Две правки без изменения сути поведения:
  - *дальность обзора по скорости* — Unit смотрит настолько, насколько успеет пройти за горизонт реакции: на полном ходу 5×5 клеток, в давке (где все заторможены) 3×3, то есть кандидатов почти втрое меньше;
  - *обход через тик* — решение пересчитывается 20 раз в секунду вместо 40, половины Unit чередуются по номеру. На горизонте 0.8 с задержка 25 мс незаметна, а решение и так сглаживается между тиками.
  - Отклонено после замера: период пересчёта по обстановке (редко, если в прошлый раз никого не нашлось). В массовом столкновении соседи есть почти у всех, поэтому выигрыша нет, а Unit, выходившие из редкого режима, возвращались к пересчёту кучно — пики выросли с 19 до 25 мс.
  - Отклонено после замера: складывать горячие данные соседей (позиция, скорость, радиус, Squad) в один массив в порядке записей сетки. Выигрыша нет — номера Unit внутри Squad идут подряд, сетка группирует их по клеткам, поэтому чтения и так были локальными; остался только лишний проход (+0.45 мс).
- **Мягкий слот — на всё движение:** внутри `SlotDeadZone` (30 см) Unit не подравнивается, дальше возвращается не быстрее «отклонение / `SlotReturnTime`» (0.8 с) — по пологой дуге. Строй становится чуть менее идеальным и живее.
- **Контакт:** толкается только перекрытие сверх допуска «плечом к плечу» (`SeparationTolerance` 10 см), мягче прежнего (`SeparationStiffness` 8 1/с). Доли уступки: стоящий держит место надёжнее и берёт 1/3 сдвига, движущийся — 2/3.
- **Теснота Squad (L1):** среднее торможение Unit Squad, усиленное в 1.5 раза (обычно заторможены только передние ряды), снижает скорость центра до `SquadCongestionSlowdown` (до 60%). Множитель меняется плавно: замедляется за ~1 с, восстанавливается за ~2 с. Это минимальная версия будущих статусов дистанции (шаг 18).
- **Порядок в тике:** сетка по позициям на начало тика → L2 + обход (намерение и инерция, затем движение) → контакт → теснота Squad → Unit Grid. Сетка строится до движения, потому что обход — часть намерения; для контакта после движения её тоже хватает (сдвиг за тик — сантиметры).
- Все параметры — CVar `algona.P2.Slot*`, `algona.P2.Avoidance*`, `algona.P2.Separation*`, `algona.P2.SquadCongestionSlowdown`; `algona.P2.Avoidance 0` и `algona.P2.Separation 0` выключают свои части. Стадии `l3grid`, `steer` (включает обход), `l3` (контакт и теснота) в `[P2 Metrics]`.

### 4h. L3 — отбор участников и общая сетка (шаг 14, 2026-09-26)

- **Отбор (broadphase):** после движения каждый Squad считает фактические границы — прямоугольник, реально занятый его Unit, с запасом на радиус Unit. В следующем тике границы расширяются на дальность обзора обхода (300 см) плюс путь за тик, и по ним строится крупная сетка Squad (клетка 20 м). Unit попадают в L3 только у тех Squad, чьи границы пересекаются с другим Squad.
- **Пара должна двигаться:** Unit попадают в L3, только если границы Squad пересеклись и при этом хотя бы один из пары движется. Без этого условия неподвижная армия целиком оставалась в L3 — в стартовой раскладке Squad стоят вплотную, и границы с запасом пересекаются почти у всех (замер: стоящая армия 2.25 мс против 1.57 до отбора).
- **Перестроение и поворот:** Squad остаётся участником L3 ещё секунду после Reform и всё время поворота, даже если рядом никого: при перестроении Unit идут через чужие слоты и могут пройти насквозь.
- **Список Unit собирается проходом по всем Unit** с проверкой признака их Squad — так он остаётся упорядоченным по возрастанию, как требует сетка (иначе пришлось бы сортировать 100 000 номеров каждый тик).
- **Одна структура на всё:** `FAlgonaTorusGrid` (бывшая сетка L3) получила размер клетки параметром и построение по прямоугольникам — элемент кладётся во все накрытые клетки. Используется и для Unit (клетка 150 см, точки), и для Squad (клетка 20 м, прямоугольники); позже так же лягут крупные Unit.
- **Старая Squad Grid удалена.** Она была отключена с P0 и хранила ячейки в словаре с точечным обновлением — это выгодно, когда объекты двигаются редко, а у нас любой Squad всегда потенциально подвижен. Для будущих задач боя и AoE та же `FAlgonaTorusGrid` подходит лучше: полная перестройка 2000 Squad дешевле поддержки словаря, а данные лежат подряд. Unit Grid (клетка 100 м, точечное обновление) оставлена: ею пользуются выбор мышью и запросы извне симуляции.

- **Замер (100 000 Unit, все потоки):** стоящая армия — весь шаг **0.91 мс** (steer 0.47, l3grid 0.20, l3 0.10) против 2.25 мс до отбора и 1.57 мс до появления отбора вообще. Стресс-сценарий не изменился (~3.3–4.3 мс): там движутся все, отсеивать некого.

### 4i. Крупные существа (шаг 15, 2026-09-27)

- **Радиус — у каждого Unit**, в плоских массивах Simulation, вместе с масштабом меша: отряды будут смешанными (щитоносцы впереди, лучники позади), поэтому размер не может жить на Squad. Squad хранит радиус по умолчанию для пополнения и наибольший радиус состава.
- **Интервал строя от самого крупного Unit:** `2 × радиус + просвет 60 см`, но не меньше обычных 150 см. Иначе крупные стояли бы телами внутри друг друга.
- **Вес при расхождении — линейно от радиуса:** подвижность = (движется ? 2 : 1) × (обычный радиус / свой радиус). Тролль вдвое шире пехотинца сдвигает его вдвое охотнее, чем наоборот. Квадрат от радиуса отклонён: разница слишком резкая.
- **Сетка соседей:** Unit крупнее половины клетки кладётся во все клетки, которые накрывает; мелкие по-прежнему занимают одну. Порог не даёт раздуть число записей: при радиусе до 75 см (клетка 150) всё работает как раньше, а платит за себя только настоящий гигант.
  - Отклонено: расширять радиус поиска у всех вместо записи по клеткам — расширение общее, один гигант на карте удвоил бы число кандидатов у всех 100 000 Unit.
- **Поворот тела — тоже от радиуса:** скорость поворота Unit обратно пропорциональна радиусу (360°/с у обычного, 180°/с при радиусе 70). Крупные разворачивались на месте слишком резво.
- **Щели строятся по всем соседям впереди**, а не только по тем, с кем вот-вот столкновение. По одному-двум соседям щель находится всегда (слева или справа от них), и крупный Unit целился в неё, делал шаг, видел других — и вилял. Видя ряд целиком, он понимает, что нигде не помещается (нужно 125 см при просветах 80), и идёт прямо, тормозя и расталкивая; пехотинцу в том же ряду щели хватает. Средние размеры получают промежуточное поведение сами, без отдельных правил и без типов существ.
  - Доли обхода и торможения остаются пропорциональными подвижности: при соотношении радиусов 1 к 2 крупный берёт на себя треть, а не «не замечает» мелкого.
- **Крупный не виляет в тесноте:** между стоящими Unit щель 80 см, а крупному с соседом нужно 125 — подходящей щели нет, и выбор прыгал между кромками каждый тик. Теперь сторона обхода держится, пока противоположная щель не станет заметно ближе (коэффициент 0.7), а если ближайшая щель дальше трёх своих радиусов, Unit не уклоняется вовсе: тормозит и протискивается, разводит его толчок.
- **Тестовое содержимое** до появления типов существ (P3): CVar `algona.P2.LargeSquadEvery` (каждый N-й отряд — 5 крупных) и `algona.P2.MixedSquadEvery` (каждый N-й — 2 крупных и 6 обычных, крупные в первой строке); размер задаётся `algona.P2.LargeUnitRadius` и `algona.P2.LargeUnitMeshScale`.
- **Presentation** получает масштаб меша в снимке Unit и умножает на него масштаб инстанса.
- **Замер (100 000 Unit, стресс-сценарий, все потоки, тестовые крупные отряды включены):** весь шаг ~4.3–5.0 мс (steer ~2.5–3.0, l3grid ~0.72–0.78, l3 ~0.81–0.99) против ~3.3–4.3 мс без крупных. Рост от того, что крупные занимают несколько клеток сетки и дают больше кандидатов, плюс отрядов стало ~2100 вместо 2000. Разовые пики 10–13 мс приходятся на тики с перестроениями.

### 4k. Пропуск обхода внутри строя — отклонено (2026-09-30)

- Идея: Unit, окружённый своими слотами, не считает обход, пока Squad идёт свободно; контактный толчок остаётся.
- Реализовано и отклонено. Выигрыш в марше оказался небольшим (`steer` 4.4–5.8 → 3.9–5.3), а гарантий не давал: контактный толчок мягкий и не запрещает перекрытие, поэтому без предвидения свои Unit могут продавливать друг друга везде, где их траектории пересекаются — при догоне отставших, при замедлении Squad, при волне от толчка в строю. Закрывать каждый такой случай отдельным признаком (перестроение, поворот, близость к слоту, встреча с чужими) — это набор частных правил вместо одного понятного.
- Для целевых 4 ядер хватает ограничения догоняющих шагов за кадр (раздел 4j): кадры остаются плавными, а симуляция при перегрузке идёт чуть медленнее реального времени.

### 4j. Защита кадров и сценарий марша (2026-09-30)

- **Догоняющих шагов за кадр — два вместо пяти** (`MaxStepsPerFrame`). При тяжёлом шаге кадр успевал прогнать пять шагов подряд, и картинка проваливалась до 20 FPS. Теперь при перегрузке симуляция идёт чуть медленнее реального времени, зато кадры остаются плавными. Это не ускорение, а защита от обвала.
- **Стресс-марш** `algona.P2.StressMarch 1`: все Squad идут в одну сторону и возвращаются обратно, не встречаясь. Нужен, чтобы отделить цену движения больших армий от цены столкновений — существующий `algona.P2.StressMove` специально сталкивает соседние ряды. В строке `[P2 Metrics]` режим виден как `stress=MARCH`.

### 4m. L1 — путь центра Squad по навигации (шаг 16, 2026-10-04)

Пока путь был отрезком, всё поведение L1 строилось вокруг прямой «центр → цель». С навигацией путь стал ломаной, и это задело режим движения, конечное направление и упреждающий доворот — они считаются теперь по пути, а не по прямой.

- **Источник пути — штатная навигация UE** (Recast NavMesh). Своя сетка проходимости не рассматривалась как первый шаг: NavMesh уже строится по геометрии уровня, учитывает постоянные и переключающиеся препятствия (как и требует ГД) и детерминирован при одной карте, то есть пригоден для server-authoritative модели. Своё понадобится только если упрёмся в производительность или в ограничения — тогда это отдельное решение.
- **Запрос синхронный, с лимитом за тик** (`algona.P2.PathQueriesPerTick`, 64). Приказ не ждёт навигацию: Squad сразу идёт по прямой (путь из одной точки — самой цели), а посчитанный путь заменяет её через несколько тиков. Групповой приказ на 2000 Squad расходится за ~30 тиков (меньше секунды) и не делает один шаг тяжёлым. Асинхронные запросы отклонены как лишняя сложность: результат всё равно применяется в фиксированном шаге, а лимит даёт ту же защиту кадра понятнее.
- **Цель приказа = конец пути.** Навигация ставит её на проходимое место: при достижимой цели это та же точка (ГД: центр останавливается ровно там, куда указал игрок), при недостижимой — ближайшая доступная. Запрос разрешает частичный путь и непроходимую цель (`SetRequireNavigableEndLocation(false)`), поэтому приказ «в стену» или за закрытые ворота доводит Squad до ближайшего достижимого места, а не отменяется и не ведёт сквозь препятствие.
- **Запас от стен даёт сама карта проходимости, а не обработка пути (пересмотрено 2026-10-07).** Recast при построении сужает проходимую зону на радиус агента, поэтому в `Config/DefaultEngine.ini` объявлены ступени агентов: `Unit` (35), `SquadNarrow` (300), `SquadWide` (700). **Карта на каждый Squad невозможна и не нужна:** каждая карта — полная перестройка Recast по уровню, а точную ширину строя разбирают препятствия для Unit (шаг 17) и проход очередью (шаг 19); карта даёт лишь запас «не скрестись о стену, когда есть место». Squad берёт самую широкую ступень, которая не шире его строя (полуширина = дальний слот плюс тело Unit, потолок — `algona.P2.PathAgentRadius`); список ступеней код читает из `SupportedAgents`, поэтому добавленная в ini строка подхватывается без правок кода. Путь по выбранной ступени держит запас от стен и точками, и отрезками — без единой пробы, детерминированно и бесплатно по времени запроса.
  - **Запас — предпочтение, а не ограничение маршрута.** Широкая карта требует двойного радиуса агента свободной ширины, поэтому как жёсткое условие она уводила Squad в обход мимо прохода, в который он помещается (видно в редакторе 2026-10-07) — а ГД прямо запрещает запрещать коридор только потому, что он уже строя. Поэтому считаются оба пути, по обычной карте и по широкой, и широкий берётся, только если он не длиннее короткого больше чем в `algona.P2.PathWideDetour` раз (1.25). Иначе Squad идёт коротким путём вплотную к стенам, и дальше это случай прохода очередью (шаг 19). Цена — два запроса на приказ вместо одного.
  - **Недостижимая цель — приказ не выполняется вовсе** (решение 2026-10-09): Squad остаётся на месте, а не идёт в ближайшее доступное место — это значило бы придумать за игрока другую цель. Допуск 150 см на случай клика у самого края проходимой зоны. Так же отменяется приказ, если пути нет вовсе; но сначала запрос повторяется от ближайшей проходимой точки, потому что в давке свои же Unit выталкивают Squad к стене, и именно из-за этого центры изредка шли сквозь стены по прямой (запасной вариант «идти прямо» для таких случаев убран).
  - Частичный путь по широкой карте принимается, только если он не дошёл лишь до самой точки приказа (она у стены, куда широкая карта не достаёт): маршрут тогда остаётся с запасом, а последний отрезок ведёт к заказанной точке. Иначе это «прохода для строя нет», и считается короткий путь.
  - **Запас на коротком пути даёт штатный `FNavMeshPath::OffsetFromCorners(Distance)`** — обработка пути, которая есть в движке и используется его же отладочным актёром `NavigationTestingActor` (поле Offset From Corners Distance, им это поведение смотрится в редакторе без нашего кода). Она находит для каждой точки пути ребро коридора, на котором точка лежит, и, если точка прижата к концу ребра, сдвигает её вдоль ребра от угла на `min(Distance, половина ребра)`: в узких воротах это ровно их середина, точки в чистом поле не трогаются. Второй проход по видимости (`bUseBetterOffsetsFromCorners`, включён в `BaseEngine.ini`) выкидывает ставшие лишними точки.
  - **Отклонено: своя сборка пути по воротам коридора** (сужение ворот на запас плюс протягивание верёвки-воронки). Реализовано и отклонено 2026-10-09 после нескольких итераций в редакторе: сужение всех ворот давало лишний крюк (у препятствий полигоны мелкие, короткие рёбра схлопывались в свои середины); сужение только по изгибам верёвки толкало путь от вершин силуэта коридора в чистом поле; сторона ворот (где «лево») определяется ненадёжно, потому что перевод координат Recast в Unreal зеркалит плоскость, и на неверной стороне воронка вырождалась в прямую — отряд изредка шёл сквозь стену одним отрезком. Всё это уже решено в движке, и правильный вывод: сперва искать готовое в UE, а потом писать своё.
  - Известное ограничение: ворота держат путь только в своих местах, поэтому вдоль длинной грани полигона запас обеспечивает лишь широкая карта; когда побеждает короткий путь, вдали от ворот он может идти ближе к стене. Полное решение — своя карта со стоимостью близости к стенам; к нему вернёмся, только если это будет заметно мешать. Предел среза угла дугой при этом равен радиусу агента (по широкой карте) или минимуму (по обычной).
  - **Отклонено: отодвигать точки готового пути от стен постобработкой.** Четыре варианта замера были реализованы и отклонены по логам в редакторе 2026-10-07: вдоль поперечной оси пути (у торца стены препятствие по диагонали позади, замер его не видит); пробой отдельных точек на навмеш (проба за тонкой стеной попадает на проходимую землю с другой стороны, `left=1477 right=1477` вплотную к стене); штатным `ARecastNavMesh::FindDistanceToWall` (в точке пути он честно отвечает «край в нуле», а ближайшая точка края совпадает с самой точкой, и направление отхода вырождается); лучами по кругу с направлением по взвешенной сумме (работает, но в вершине края навигация не находит стартовый полигон, все лучи отвечают нулём, и точка остаётся на месте). Главное же — **принципиальный предел**: постобработка держит на расстоянии только точки ломаной, а строй идёт по отрезкам между ними, и внутри полигона коридора отрезок свободно прижимается к стене. Численная модель воронки по суженным «воротам» коридора подтвердила то же: узкий проход она проходит ровно по центру, а у торца стены отрезок между воротами всё равно проходит в 124 см от угла при запасе 739.
- **Сглаживание углов — погоня за точкой.** Центр ведёт не сама точка поворота, а точка на пути впереди него (`FollowAlgonaPath`): пока Squad едет, она скользит по пути, направление меняется постепенно, и угол срезается дугой. Расстояние впереди по умолчанию равно радиусу дуги, по которой строй вообще способен повернуть (скорость, делённая на угловую скорость; у широкого строя он больше), в пределах 150–3000 см; подбор на ходу — `algona.P2.PathLookahead`. Сверху оно ограничено запасом, который этот путь реально получил: при построении пути запоминается наименьший просвет у его поворотов, и срез не может выйти за него (`PathMaxLookahead`, срез ≈ 0.9 расстояния погони). В узком коридоре это само собой делает поворот круче, и центр идёт ближе к ломаной. Отклонён вариант «переключать точку заранее»: направление движения менялось рывком, строй при этом ехал боком, пока доворачивал.
- **Остаток пути** (от центра до текущей точки плюс длина оставшихся отрезков) заменил прямую до цели в торможении у цели, упреждающем довороте марша и применении ширины строя. На срезанных углах он немного завышен, то есть торможение чуть осторожнее — это безопасная сторона.
- **Что считается по пути, а не по прямой:** режим движения (шаг вбок / лицом вперёд / марш) — по длине всего пути; конечное направление без явного приказа — по последнему отрезку пути. Направление, заданное игроком (зажатый ПКМ) и групповым приказом, путь не меняет.
- **Пересчёта пути нет:** NavMesh учитывает постоянные препятствия, а динамические (Unit) по ГД маршрут не меняют — на них отвечает L3. Пересчёт появится вместе с переключающимися препятствиями (ворота) и проходом очередью.
- **Отладка и выключение:** `algona.P2.Path 0` возвращает прямые пути (сравнение и замер), `algona.P2.DebugPath 1` рисует путь выбранных Squad. Стадия `path` добавлена в строку метрик. Если навигации в мире нет, Squad идут по прямой, и об этом один раз пишется предупреждение в лог.
- **Настройки NavMesh** записаны в `Config/DefaultEngine.ini`: агент — обычный Unit (радиус 35, рост 170), клетка 50 см и плитка 40 м вместо стандартных 19 см и 10 м. На почти километровой ровной карте стресс-теста это даёт в 16 раз меньше плиток при точности, которой для пути центра хватает с запасом.

### 4n. Спавн армии командой и карта проверок (шаг 16a, 2026-10-04)

Инструменты проверок, не игровая механика. Понадобились на шаге 16: проверять пути удобно на подготовленной карте и на десятке отрядов, а не на 100 000 Unit, расставленных сеткой от начала координат.

- **Армия при старте мира не создаётся.** `algona.P0.UnitCount=0` в `Config/DefaultEngine.ini`: запуск PIE больше не тратит время на создание сотен тысяч Unit. Значение больше нуля по-прежнему создаёт армию сразу, как было.
- **`algona.P2.Spawn <юнитов> [размер отряда] [угол строя]`** досыпает армию туда, куда смотрит камера, лицом от камеры, но по ближайшей оси мира: камера RTS смотрит по диагонали (`CameraYaw` 45°), а геометрия карты стоит по осям, и диагональный строй у прямой стены только мешает смотреть на движение. Третий аргумент задаёт угол строя явно. Команда **`algona.P2.Clear`** убирает всех. Команды живут в игровом модуле, потому что им нужна камера игрока: Simulation получает уже готовые точку и направление (`SpawnArmy`, `ClearArmy`) и о локальном игроке по-прежнему ничего не знает.
- **Досыпание, а не замена:** Unit создаются в хвост плоских массивов, индекс нового Unit (`UnitId - 1`) продолжает нумерацию, поэтому индексы прежних Unit остаются верными. `InitializeUnitState` заменён на `ResizeUnitState` (добавленные элементы получают значения по умолчанию, лишние отбрасываются). Это нужно не только для удобства: тем же путём в P3 пойдут подкрепления.
- **Правило размещения — одно на два случая** («встал в стену» и «встал в чужой отряд»): отряды занимают клетки шага раскладки, ряды назад от точки спавна, внутри ряда от середины вправо; клетка годится, только если прямоугольник площадки целиком лежит на проходимой земле (проверяются центр и четыре угла через `ProjectPointToNavigation`) и в нём нет чужих Unit (кандидаты из Unit Grid, затем точная проверка по месту). Не годится — берётся следующая клетка; перебор ограничен четырьмя клетками на отряд. Итог пишется в лог: сколько Unit и Squad встало, сколько клеток пропущено, не кончилось ли место. Unit, которым места не нашлось, удаляются — армия не остаётся с Unit без Squad.
  - Отклонено: полагаться на L3 (расталкивание растащило бы наложившиеся отряды, но это выглядит кашей и портит замеры тесноты) и проверять только центр отряда (дешевле, но отряд наполовину висел бы в стене).
  - Слот внутри препятствия на спавне не проверяется: гарантируется только площадка отряда. По ГД такой Unit должен встать в ближайшее доступное место к слоту — это шаг 17.
  - Если навигации в мире нет, проверка проходимости отключается (один раз в лог), отряды встают как есть.
- **Раскладка армии** стала примерно квадратной (клеток в ряду — корень из их числа) вместо прежних 40 отрядов в ряду, и ориентируется по направлению спавна. Поэтому полосы стресс-сценария считаются теперь по положению Squad (`StressBandWidthCm` 2000 см по Y), а не по номеру: номер больше не говорит о месте. Для сравнимых со старыми замерами стресс-прогонов армию стоит спавнить, глядя вдоль +X; точка и направление спавна пишутся в лог.
- **Карта `P2_Movement`** наполняется редакторной командой `algona.P2.BuildMovementMap` на пустом уровне (геометрия описана числами в коде, а не расставлена мышью, поэтому площадку можно переделать правкой координат и повторным запуском — свои актёры с префиксом `AlgonaP2_` команда удаляет и создаёт заново). Содержимое: ровная земля 1200x1200 м с верхом ровно на Z = 0, Г-образная стена (срез угла дугой), узкий проход 2 м (запас по бокам и будущий проход очередью), широкие ворота 10 м, круглая скала 30 м в открытом месте (обход с двух сторон), закрытый двор (цель внутри недостижима — частичный путь), свет с небом, том границ навигации на всю землю. `GameDefaultMap` и `EditorStartupMap` переключены на неё.

### 4p. Статические препятствия для Unit (шаг 17, 2026-10-10)

Маршрут Squad обходит препятствия с шага 16, но отдельный Unit о мире не знал: в давке его выталкивало сквозь стены. Шаг 17 закрывает три правила ГД — Unit не проходит сквозь постоянную геометрию; слот, оказавшийся в непроходимом месте, заменяется ближайшей доступной позицией; такой Unit не замедляет Squad и не заставляет его ждать.

**Стены берутся из границы проходимой зоны навмеша** — это те же линии, которыми редактор рисует край навигационной карты. Источник — рёбра-стены каждого полигона (`ARecastNavMesh::GetPolysInTile` + `GetPolyWallSegments`). Ключ к точности: Recast при построении сужает проходимую зону на радиус агента, поэтому граница карты Unit (радиус 35) — ровно та линия, на которой центр Unit касается стены плечом. Запас обычному Unit не нужен (0), крупному нужен ровно `радиус − радиус агента`; подстройка под воксельную точность навмеша — `algona.P2.WallMargin`.

- Запекание одноразовое (навмеш статичен): при первом шаге с армией, заново по сигналу `OnNavigationGenerationFinishedDelegate` и по команде `algona.P2.RebuildWalls`.
- **Дырка в движке (найдена падением 2026-10-10):** `GetAllNavMeshTiles` отдаёт ссылки и на пустые слоты пула плиток — у них есть salt, поэтому ссылка не нулевая, но данных нет, — а `GetEdgesInTile` разыменовывает `Tile->header` без проверки и падает на таком слоте (`EXCEPTION_ACCESS_VIOLATION` по адресу 0x16, то есть смещение поля от нулевого указателя). `GetPolysInTile`, через который стены собираются теперь, заголовок проверяет сам. Отрезки лежат в той же `FAlgonaTorusGrid` (клетка 300 см), что соседи и Squad, поэтому Unit ищет стены тем же поиском 3×3.
- **Сторона проходимости — от центра полигона-владельца.** Каждый отрезок-стена принадлежит ровно одному полигону навмеша, полигоны выпуклые, и их центр поэтому всегда лежит с внутренней стороны каждого ребра. Нормаль смотрит в сторону этого центра — точно для каждого отрезка в отдельности, без догадок о порядке вершин и без проб навмеша. В UE `getPolyWallSegments` возвращает только стены (сохранение порталов отключено прямо в коде Detour), включая куски рёбер на стыках плиток, не прикрытые соседом.
  - **Отклонено после проверки в редакторе (2026-10-14):** рёбра плитки через `GetEdgesInTile`, нормаль влево от направления отрезка, общее соглашение — голосованием по 64 отрезкам с пробой `ProjectPointToNavigation` в 30 см от середины. Рёбра плитки — это рёбра детальной сетки, и порядок их вершин не обязан совпадать от отрезка к отрезку; голосование ловит только общий переворот. С клеткой 50 см это не проявлялось, с клеткой 25 см и меньшей вольностью контура отрезков стало больше и мельче — и Unit начало затягивать в стену с расстояния до 150 см. Урок: **нельзя выводить знак из соглашения, которое проверено выборкой, когда его можно вычислить для каждого элемента точно.**
- **Нормаль обязательна, а не удобна:** в покое обычный Unit стоит ровно на линии, и направление «от ближайшей точки к центру» там вырождается в нуль. На этом же в шаге 16 вырождался `FindDistanceToWall`.
- Отклонено: **борта коридора пути** — так делает сам движок для Mass (`UMassNavMeshNavigationBoundaryProcessor` складывает левые и правые стороны ворот короткого пути в `FMassNavigationEdgesFragment`). Данные бесплатны, но работают только у движущегося Squad с путём, стоящий у стены стен не видит, а строй шире коридора — у Unit на краю борт коридора не его стена и нормаль указывает не туда.
- Отклонено: **запрос к навигации на каждый Unit** (`FindEdges`, `FindDistanceToWall`) — запрос с выделениями и блокировкой, микросекунды на вызов; 100 000 Unit не проходят даже при опросе раз в секунду (2500 запросов на тик).
- Отклонено: **своя растровая карта проходимости** (битовая маска или поле расстояний) — дублирует работу Recast, память по всей карте (1200×1200 м при 50 см — 5.8 млн клеток), а нормали по осям клеток заставляют Unit идти вдоль стены лесенкой.
- Отклонено: **запросы к физике мира** — Simulation начала бы зависеть от акторов и физической сцены, и стоит это дороже запросов к навигации.

**Жёсткая часть — зажим позиции, не пружина.** Отдельная стадия после расталкивания (`ClampUnitsToWalls`, стадия `walls` в метриках): Unit, оказавшийся за границей, возвращается на неё ровно, и его скорость теряет составляющую в стену — это же даёт скольжение вдоль стены. Пружинный толчок, как между Unit, отклонён: для живого соседа продавливание нормально, для скалы — нет.

- **Решает только ближайший к Unit элемент границы** (по настоящему расстоянию до отрезка, а не до его бесконечной линии): по нему определяется, за какой стороной границы Unit, и куда его вернуть. Если ближайшая точка — общая вершина двух отрезков, сторона берётся по их средней нормали: у вершины нормаль одного отрезка врёт. Это обычная модель «точка против многоугольника» из физических движков. Два прохода за тик — для угла, где после возврата от одной стены ближайшей становится соседняя.
- Перед границей выталкивание радиальное, от ближайшей точки: в проходе Unit расходится с обоими краями и встаёт посередине, у торца стены обходит угол.
- **Отрезки по месту — только с проверкой настоящего расстояния (дефект, найден 2026-10-14).** Сетка стен свёрнута в тор, и среди кандидатов поиска 3×3 всегда есть отрезки с другого конца карты, попавшие в те же корзины. Контракт сетки это прямо оговаривает («расстояние проверяет вызывающий код»), а первая версия модели «решает ближайший элемент» его нарушила: в открытом поле, где настоящих стен рядом нет, ближайшим оказывался отрезок за сотни метров, и зажим переносил туда Unit — при спавне и на ходу Unit «исчезали». Воспроизведено численно с моделью тора: скачок 383 м. Теперь отрезки по месту отдаёт только `FAlgonaWallField::ForEachSegmentNear` — с проверкой настоящего расстояния (300 см) и высоты внутри; сырого доступа к кандидатам сетки снаружи нет, поэтому забыть проверку больше негде. Тест `Algona.P2.UnitWalls.Locality` ставит две стены ровно на период тора друг от друга.
- **Отклонено после проверки в редакторе (2026-10-14): складывать поправки от всех отрезков, за линией которых оказался Unit в пределах 150 см** (`AlgonaWallMaxDepthCm`). Два провала одной модели: длинная линия чужого отрезка «захватывает» Unit издалека, а на мелких скосах углов остаются места, за которые не отвечает ни один отрезок (Unit за линией, но вне промежутка каждого), — Unit, попавший туда, уже не выходил. Глубина 150 см была подпоркой именно против захвата издалека; у модели ближайшего элемента захвата нет вообще, и законно стоящего по другую сторону стены Unit не тянет сквозь неё — для него ближайшая граница своя. Число 150 см осталось только в намерении (обход и скольжение) как фильтр «эта стена у меня за спиной».
- Правило слота использует ту же модель, но только среди стен, перед которыми стоит **центр Squad**: у толстой стены две стороны, и слот выдавливается на сторону отряда, а не на дальнюю, куда идти в обход. Сторона сначала выбиралась по позиции самого Unit — отклонено после проверки (2026-10-14): Unit в толпе толкается, и его цель прыгала вместе с ним. Центр стоящего Squad неподвижен, поэтому цель стабильна.

**Терпение у стены (2026-10-14).** Несколько слотов в стене (строки одна за другой) выдавливаются правилом слота в одну и ту же точку у грани: одна точка — несколько Unit, и они толкались вечно. Никакая геометрия этого не снимает: развернуть слоты наружу значит положить их на слоты передних строк. Стандартное для RTS решение — терпение: Unit стоящего Squad у стены помнит, насколько близко к цели подошёл, и если 1.5 с не приблизился хотя бы на 20 см, встаёт там, где стоит, до следующего приказа или Reform. Это и есть «ближайшая доступная позиция» ГД, когда к самой точке не пробиться. Такой Unit получает тот же признак `SlotBlockedFlags`, что и Unit со слотом в стене. Идущий к цели Unit продвигается на сотни сантиметров в секунду, поэтому сдаётся только упёршийся.

- Сброс без прохода по всем Unit: у Squad есть номер эпизода стояния, он растёт при остановке и при Reform стоя; Unit хранит номер, к которому относится его терпение, и при несовпадении начинает заново.
- Ограничение: пока только у Squad рядом со стенами. Та же вечная толкотня возможна и без стен (два стоящих Squad внахлёст); общее правило «упёрся — встал» — это статусы дистанции шага 18.

**Поворот тела по ходу — с гистерезисом скорости намерения** (по ходу выше 60 см/с, обратно ниже 30). Прежний порог — 1 см/с: в толкучке у стены остаток намерения крошечный и меняет знак каждый тик, и Unit разворачивался влево-вправо без остановки. Медленно переминающийся Unit теперь смотрит по направлению Squad.
- Высота отрезка хранится (`MinZ`, `MaxZ`) и сравнивается с высотой Unit с допуском 200 см: на многоуровневой карте стена моста не мешает тому, кто идёт под мостом.

**Мягкая часть — стены в том же выборе щели, что соседи.** Отрезок обрезается по полосе хода Unit `[0, 300 см]` и проецируется на его поперечную ось занятым интервалом; подвижность стены нулевая, поэтому доля обхода Unit равна единице (уступать стене нечем). Обрезка по полосе — главное в этом: стена сбоку занимает интервал в стороне и ход не перекрывает, иначе Unit тормозил бы всю дорогу вдоль стены. Отрезки одной стены сливаются в один интервал (иначе они вытеснили бы соседей из таблицы на 12 мест), а проход между двумя стенами остаётся разрывом, потому что их интервалы не пересекаются. Стена поперёк хода добавляет торможение по срочности, как встречный Unit.

- Намерение теряет **излишек** хода в стену, а не всю составляющую: скорость сближения ограничена «остатком до запаса, делённым на время гашения» (0.1 с). Далеко от стены ограничения нет, вплотную оно гасит ход полностью, и дальше намерение остаётся только вдоль стены — это и есть скольжение. Поворот тела считается по намерению, поэтому Unit заодно смотрит вдоль стены.
  - **Первая версия (отклонена после проверки в редакторе 2026-10-10):** обнулять всю составляющую в стену, когда Unit ближе 100 см к ней. Порог сам стал стеной — Unit останавливался в метре от камня и упирался в воздух. Урок общий: порог «ближе X — не двигаться туда» в движении всегда виден как невидимая преграда на расстоянии X; ограничивать надо скорость сближения, а не разрешение сближаться.

**Запас считается от фактического сужения, а не от объявленного радиуса агента.** Recast сужает проходимую зону на **целое число клеток**: `walkableRadius = ceil(AgentRadius / CellSize)`, то есть при клетке 25 см и радиусе агента 35 это 50 см, а не 35. Код берёт это число (`ceil(AgentRadius / CellSize) * CellSize`), поэтому крупный Unit получает запас ровно на своё превышение над сужением, а обычный — ноль и стоит на самой линии. Между его телом и камнем остаётся ~15 см: это разница между сужением (50) и радиусом тела (35).

- **Отклонено после падения в редакторе (2026-10-14): компенсировать этот зазор отрицательным запасом.** Расчёт выглядел точным (−15 см, тело касается камня), но провалился дважды. Во-первых, запас применялся как **цель**, а не как предел: едва Unit переступал линию, поправка утаскивала его на все −15 см, и это читалось как телепорт в стену. Во-вторых, и это важнее, компенсировать нечего: контуру навмеша разрешено отходить от воксельной границы на `MaxSimplificationError` (0.75 клетки, 19 см) **в обе стороны**, то есть неопределённость положения линии того же порядка, что и сам зазор. Заходить за линию по расчёту нельзя — те самые 15 см и есть запас на эту неопределённость. Остаётся только ручной `algona.P2.WallMargin` в минус (не глубже клетки) как осознанный размен точности на вид.
- Правило, которое из этого следует: **отрицательный запас — всегда предел («можно зайти не глубже»), а не цель («нужно стоять на такой глубине»)**. В `GetAlgonaWallCorrection` это отдельная ветка, покрытая тестами.

**Точность границы — настройка навмеша, а не постобработка (2026-10-10).** Контур навмеша кладётся по границам вокселей, а воксельная решётка привязана к плитке, а не к стене, поэтому при клетке 50 см граница у одной стороны стены оказывалась ближе, чем у другой, до полуметра, а углы срезались наискось (видно в `algona.P2.DebugWalls 2` по нормалям не под 45/90°). Это данные, а не обработка: никакая постобработка отрезков не вернёт точность, которой в них нет. Поэтому в `Config/DefaultEngine.ini` клетка уменьшена вдвое (25 см, цена — вчетверо больше вокселей на плитку), а `MaxSimplificationError` снижен с 1.3 до 0.75 клетки (32 см вольности контура вместо 65). Сращивание почти коллинеарных отрезков при запекании рассматривалось и не делалось: оно убирает только мелкую пилу, а перекос границы оставляет на месте.

**Правило «слот внутри препятствия»** применяется только у стоящего Squad — это и есть случай ГД «финиш рядом с препятствием». Слот выдавливается из стены по нормали того отрезка, перед которым стоит сам Unit (у стены две стороны, и выдавливать нужно на ту, где Unit есть), и Unit получает признак `SlotBlockedFlags`: его теснота не идёт в сводку Squad, поэтому строй из-за него не сбавляет ход и не ждёт. Статусы дистанции (шаг 18) читают тот же признак. Пока Squad идёт, правило не нужно: слот через стены проносит постоянно, и там работают обход и зажим.

- Отклонено: **обрезать отрезок «Unit → слот» по стене** — бесплатно и не требует нормалей, но даёт точку на подходе, а не ближайшую к слоту: при подходе вдоль стены Unit встал бы не там, где ближе всего к слоту.
- Отклонено (оставлено в запасе): **проекция слота запросом к навигации** — точная «ближайшая доступная точка», но это запрос на слот, то есть 100 000 запросов в момент, когда вся армия встала; понадобился бы бюджет на тик, как у путей.
- Если слот глубже 300 см внутри препятствия, ближний поиск ничего не находит: Unit упирается, и его держит зажим. Это естественный откат, а не отдельная ветка кода.

**Цена.** Признак «рядом со Squad есть стены» считается раз за тик по границам Squad против редкой решётки занятости (клетка 20 м, таблица 256 x 256 бит — 8 КБ, период свёртки 5.1 км). Unit отрядов вдали от стен не платят ничего.

**Squad у стены попадает в L3 целиком** — и обработку стен, и расталкивание соседей. Сперва стены были сделаны независимо от отбора участников L3 (дешевле: одинокий Squad у стены в L3 не попадал, но сквозь стену не проходил). **Отклонено после проверки в редакторе 2026-10-10:** у стоящего отряда у стены зажим по стенам двигает Unit, а расталкивания нет — пара стоящих Squad в L3 не попадает, — и Unit в этой толкучке проходили друг сквозь друга. Если позиции двигает что-то одно, второе обязано работать вместе с ним. Заодно Squad у стены считается «движущимся» для правила пар, поэтому втягивает в L3 и стоящего рядом соседа.

- Свёртка сетки стен в тор даёт лишних кандидатов (корзин примерно по числу отрезков, а отрезки разбросаны по карте), но масштабируется сама: больше стен — больше корзин. Настоящее расстояние проверяет вызывающий код, поэтому это только цена, а не ошибка.
- Отладка: `algona.P2.DebugWalls 1` — запечённые отрезки вокруг камеры, `2` — ещё и нормали (видно, какую сторону симуляция считает проходимой). Выключатель — `algona.P2.Walls 0`.
- Чистая математика стен — `Source/AlgonaSimulation/Public/Spatial/AlgonaWallField.h`, покрыта тестами `Algona.P2.UnitWalls.*`; числа проверены численной моделью до сборки.

### 4q. Луч центра Squad (2026-10-10)

У выбранного Squad рисуется вертикальный белый луч высотой 10 м и радиусом 6 см ровно в `CenterLocation` (`algona.P2.DebugSquadCenter`, включён по умолчанию). Центр — программная точка, а Unit вокруг неё отстают, уклоняются и расталкиваются, поэтому по строю не видно, где центр на самом деле и как он ведёт себя на повороте и у препятствия. Значение берётся без сглаживания и поправок: луч должен показывать состояние Simulation, а не красивую версию его.

- Рисуется теми же инстансами, что круги выбора (второй `UInstancedStaticMeshComponent` в `AAlgonaSelectionPresentationActor`): стандартный цилиндр движка с материалом `M_SquadCenterBeam` (Unlit, Opaque, белый). Материал создаётся редакторской командой `algona.P2.BuildSquadCenterBeamMaterial` — тем же способом, что материал круга выбора.
- Масштаб и подъём считаются по габаритам самого меша (`GetBoundingBox`), а не по предположению о его точке привязки: низ луча оказывается ровно в заданной точке независимо от того, где у цилиндра pivot.
- Отладочная отрисовка (`DrawDebugCylinder`) отклонена после проверки: она даёт сетку из линий, а не сплошное тело.

### 5. Методика замеров

- Время каждой стадии измеряется внутри одного fixed step.
- Отчёт выводится по реальному времени (раз в N секунд), а не после N шагов.
- При перегрузке `FAlgonaFixedStepAccumulator` выполняет до 5 шагов за кадр, поэтому время кадра нельзя трактовать как стоимость одного шага.
- Каждый шаг реализации сравнивается с базовой линией.

## Шаг 7 — управление мышью (спецификация и решения)

Шаг делится на части; после каждой — сборка, проверка, коммит.

### 7a. Выбор
- **Клик ЛКМ** по Unit выбирает его Squad. **Shift+клик** — добавить к выбору. **Клик по пустой земле** без Shift снимает выбор.
- **Индикация выбора** — только красные контурные круги под каждым Unit выбранных Squad. Радиус круга = `UnitRadius` × 1.5 (сейчас `UnitRadius` = 35 см, свой у разных типов существ; тот же радиус позже использует L3).
- **Зажатый ЛКМ — рамка:** выбираются все Squad, хотя бы один Unit которых попадает в рамку; **Shift+рамка** — добавить. Проверка в экранных координатах: отрезок Unit «ноги–голова» (170 см) плюс радиус проецируется через закэшированную матрицу камеры и сравнивается с рамкой. Проекция рамки на землю отклонена (не ловит Unit, у которых в рамке только голова).
- **Реализация:** клик и Shift+клик — луч курсора против вертикального цилиндра Unit высотой 170 см. Радиус попадания = max(`UnitRadius`, 0.55 × наибольший интервал строя), в пределах 50–300 см (сейчас 82.5 см): больше половины интервала, поэтому клик между строками или рядом с Unit попадает в Squad; при пересечении зон выбирается ближайший к камере Unit. Коробка строя отклонена — при движении и в бою строй не прямоугольный.
- **Рамка:** рисует `AAlgonaHUD`; отбор при отпускании ЛКМ полным перебором Squad (ранний выход на первом попавшем Unit), матрица камеры берётся один раз. Экранный радиус Unit учитывается расширением рамки.
- **Круги:** `AAlgonaSelectionPresentationActor` — `InstancedStaticMesh` на `/Engine/BasicShapes/Plane` с материалом `M_SelectionRing` (Unlit, Masked). Материал создаёт редакторская команда `algona.P2.BuildSelectionRingMaterial` в `/Game/Algona/Presentation/Selection`.
- **Технический долг:** круги и попадание используют позиции Simulation (40 Гц) без интерполяции Presentation; земля считается плоской (Z = 0); в мультиплеере клиент будет выбирать по данным Presentation, а не Simulation.

### 7b. Приказ ПКМ
- **Один Squad:** центр идёт в точку клика. Конечное направление — направление **последнего отрезка пути**, а не вектор «старт → цель» (пока путь прямой, это совпадает). Конечное направление хранится в приказе отдельным полем; по прибытии Squad принимает его (пока мгновенно, плавно — на шаге поворота).
- **Несколько Squad:** точки центров раскладываются генератором формы: длина строки = ⌈√N⌉ («квадрат»), неполная строка по центру (4 Squad → 2×2, 3 Squad → 2 + 1 по центру). Расстояние между точками по ширине и по глубине = **длина самого длинного Squad (расстояние между крайними Unit) × 1.1**; небольшое пересечение допустимо.
- **Направление группы** одно для всех Squad; пока — вектор от центра группы (среднего центров Squad) к точке приказа; прежний вариант «от ближайшего Squad» заменён 2026-09-17 (будет переработано вместе с путями по миру). Squad назначаются на точки по текущему положению (передние — в передние, правые — в правые), чтобы пути не перекрещивались.
- Групповой приказ — одна команда «Squad → точка»; раскладку точек считает Simulation.
- **Реализация:** команда `MoveGroup` (список `SquadIds` + точка) раскладывается в `ApplyMoveGroupCommand`; клик ПКМ по одному Squad — тот же `MoveGroup` из одного Squad. «Длина Squad» для интервала точек — наибольшее из ширины и глубины раскладки слотов (не меньше `SlotSpacing`), чтобы глубокие Squad не накладывались. Назначение: Squad сортируются по проекции на направление группы (спереди назад), режутся на строки по ⌈√N⌉ и внутри строки сортируются слева направо; точки упорядочиваются так же. Команда `Move` получила поля `FinalDirection` (ноль — направление пути) и `RowLength` (0 — не менять); Squad хранит `FinalFacingDirection` и `PendingRowLength`.

### 7c. Зажатый ПКМ (только для одного выбранного Squad)
- При нескольких выбранных Squad — красное сообщение на экране и обычный групповой приказ по точке нажатия.
- Нажатие задаёт **целевую точку центра**. Начальный вектор направления — от текущего центра к цели. Движение мыши **вокруг** точки вращает этот вектор; расстояние до точки не важно.
- Предпросмотр: красные круги всех слотов в целевой позиции и стрелка направления в передней части Squad. Слоты предпросмотра строятся той же функцией, что итоговые слоты Simulation.
- **Зажатый ПКМ + Shift:** движение мыши ближе или дальше от точки меняет ширину строя симметрично от центра; чувствительность ~1 шаг длины строки на ~1 см экрана (~40 px, константа). Направление в этом режиме фиксировано. Отпускание Shift возвращает вращение без скачка (начальные вектор и угол перезапоминаются). Цикл можно повторять, пока ПКМ зажат.
- Длина строки ограничена min(число Unit в Squad, 50).
- **Ширина в составном приказе** начинает применяться за **10 м до цели**; если путь короче — сразу.
- **Защита от бага «итоговое направление не совпадает со стрелкой или перпендикулярно»** (встречался в прошлых реализациях):
  - угол считается только на плоскости земли (курсор проецируется на землю каждый кадр), не в экранных координатах;
  - мёртвая зона у целевой точки: вращение начинается после отхода курсора на N пикселей, начальный угол запоминается в этот момент;
  - одно хранимое значение «вперёд» (ось X раскладки); стрелка и слоты строятся из него;
  - вращение = начальный вектор, повёрнутый на (текущий угол − начальный), с приведением к [−180°, 180°], без накопления приращений;
  - в приказ уходит ровно последнее показанное состояние, а не пересчёт по позиции мыши при отпускании;
  - движение не перезаписывает конечное направление; цель задаётся центром, а не первой строкой.
- **Реализация:** мёртвая зона 20 px, шаг ширины 40 px (константы в `AlgonaPlayerController.cpp`). Предпросмотр появляется после выхода из мёртвой зоны или нажатия Shift; без этого отпускание ПКМ — обычный приказ по пути. Круги предпросмотра идут в тот же `InstancedStaticMesh`, что круги выбора; стрелка и сообщение рисуются в `AAlgonaHUD`. Точка слота в мире считается общей функцией `GetAlgonaSlotWorldLocation` (та же формула, что в конвейере движения). Приказы пока отправляются в Simulation напрямую из контроллера; в мультиплеере — через запрос клиента серверу в ту же очередь команд.

### Ввод
- Пока прямой опрос клавиш в `AAlgonaPlayerController` (как у камеры). Переход на Enhanced Input — после полировки боя или после путей по миру.

## Устаревшее в ГД-документе

- Движение Unit через Mass Avoidance → собственный L3-E.
- `FMassNavigationEdgesFragment` для геометрии мира → своя обработка статических препятствий (решается отдельным шагом).
- Деление скорости `0.5 / 0.5` между движением и поворотом → отменено, оба с полной скоростью; скорость крайнего слота при повороте — 1.0 скорости Squad вместо 1.25 (раздел 4d).
- Зеркальная таблица слотов при развороте → отражается сама раскладка, Unit не двигаются (раздел 4d).
