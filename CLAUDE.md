# Хроники Альгоны (AlgonaRTS)

## О проекте

Hybrid RTS/TBS с RPG-элементами. Структурный референс — The Lord of the Rings: Battle for Middle-earth II (не клон). Состав систем: RTS-сражения, строительство, экономика, армии и отряды, герои и их развитие, глобальный пошаговый (TBS) слой.

Мир и лор прорабатываются отдельно от кода (см. worldbuilding-репозиторий/базу) — лор определяет, что есть в мире, игровой дизайн решает, как это становится механикой.

Проект рассчитан на одного разработчика уровня Junior-Middle. Главный приоритет — чтобы разработчик сам полностью понимал весь код и архитектуру, а не чтобы агент делал всё непрозрачно за него.

## Текущий статус

Архитектура была перезапущена с нуля (прежняя реализация удалена, разработка продолжается с более строгим личным контролем кода).

Этапы: **P0 — Модуль симуляции**, **P1 — Модуль визуализации**, **P2 — структура отрядов и движение**, **P3 — боевая система**.

P0 и P1 отполированы. Сейчас начинается P2.

## Жёсткие требования (не менять без отдельного обсуждения)

- Целевой масштаб для проверки всех механик — **100 000+** боевых сущностей одновременно (P0/P1 уже показали хороший результат на 100к). В финальной игре ориентир может быть уменьшен при необходимости — это стресс-тест, не обязательный минимум продукта.
- Инвариант: **юнит всегда потенциально подвижен**, даже когда стоит на месте — архитектура не должна исходить из того, что большая часть армии статична.
- **Simulation отделена от Presentation.** Simulation state не зависит от визуализации; Presentation/rendering заменяется независимо от Simulation Core.
- **Actor-per-unit не используется.** Для массового отображения — инстансированное представление.
- **Мультиплеер обязателен**, учитывается в архитектуре с ранних этапов. Для production — server-authoritative модель.
- Движок — **Unreal Engine 5.8.x**. Технические решения и API-поведение должны рассматриваться именно применительно к этой версии, не к соседним.

## Принцип принятия решений

На существенных архитектурных развилках — сначала 3–5 разумных альтернатив с анализом рисков, и только потом фиксация решения.

Минимальные изолированные эксперименты — **только при реальной неуверенности** в решении, не как обязательный шаг на каждом шаге.

Не менять рабочий архитектурный путь только потому, что появился другой экспериментальный вариант, и не решать локальную проблему ценой будущей архитектуры.

## Документация решений (`Docs/`)

Папка `Docs/` в репозитории хранит принятые архитектурные решения по каждому этапу отдельно (P0, P1, P2, ...). Перед тем как предлагать архитектурное изменение — сверяться с уже зафиксированными там решениями, чтобы не предлагать заново то, что уже было рассмотрено и отклонено, и не противоречить принятому без явного пересмотра. Значимые новые решения после обсуждения — фиксировать соответствующей записью в `Docs/` для актуального этапа.

## Зафиксированный baseline (P0)

- **Unit Grid** активна, размер ячейки — 10 000 см (100 м), обновляется при создании/перемещении юнита.
- **Squad Grid** сохранена в коде, но отключена: `EnableSquadSpatialGrid = false`. Не включать автоматически без отдельной необходимости.
- `ExportUnitSnapshotsForUnitIds` читает состояние Unit напрямую из плоских массивов Simulation по `UnitId` (пересмотр в P2, шаг 6a; прежняя гибридная схема «<6% / ≥6%» удалена). Сортировка по `UnitId` перед экспортом убрана — не возвращать.
- **Состояние Unit** (позиция, поворот, скорость, `SquadId`, `SlotIndex`) — источник истины в плоских массивах Simulation Subsystem; Mass-сущность Unit хранит только `UnitId` и тег (P2, шаг 6a, см. `Docs/Architecture/ADR_P2_Movement_Architecture.md`).
- Термин `Soldier` в исходниках заменён на `Unit`.
- Временный отладочный код (режимы/команды/диагностические логи промежуточных экспериментов) удалён и не считается частью целевой архитектуры.

## Presentation

Потенциальный bottleneck: передача transform каждого инстанса с CPU каждый кадр при большом числе видимых юнитов. GPU-интерполяция рассматривалась как возможное направление, но **не зафиксирована** как решение — не считать её принятой архитектурой.

## Графика и камера

Рассматривается отключение Lumen и других тяжёлых функций UE ради производительности при сохранении «приятной» RTS-графики (цель — не максимально примитивная картинка).

Камера — **полностью перспективная проекция** (вопрос закрыт). Ортографическая камера не используется и должна быть удалена из кода, если где-то ещё осталась.

## Термины проекта

Simulation Core, Presentation/Representation, Unit, Squad, Unit Grid, Squad Grid, SimLOD, Fixed-step, Command Queue, Unit Snapshot, Reform.

## Комментарии и стиль кода

Крупные логические блоки кода помечаются пояснительными комментариями — на русском языке. C++/Unreal-идентификаторы, имена классов/методов/переменных, API-термины — не переводятся, остаются как есть.

Минимализм в структуре: не плодить лишние сущности и абстракции, но не упрощать содержание там, где сложность оправдана реальными требованиями (масштаб, мультиплеер).

## Правила работы агента в этом репозитории

- **Не пытаться билдить проект для проверки каждого изменения.** Финальная сборка всё равно происходит через редактор Unreal Engine вручную, и билд из агента почти не даёт полезного сигнала сверх обычной проверки кода/синтаксиса — только тратит впустую лимит и время. Запускать полную сборку только по явному запросу пользователя.
- **Объяснять архитектурные решения на уровне Junior-Middle, не сеньора.** Пользователь — соло-разработчик, не эксперт по ECS/pathfinding/многопоточности. При первом упоминании термина или аббревиатуры (ADR, ORCA, RVO, TTC, broadphase, Jacobi-схема и т.п.) — коротко пояснять, что это и зачем, одной фразой. Каждое решение и каждую альтернативу сначала объяснять сутью на простом языке — что происходит и почему это работает, — и только потом переходить к оценкам производительности, константам и построчным ссылкам на код. Это про слой объяснения поверх точных формулировок, а не про упрощение самих формулировок — точность решений не жертвуется ради простоты текста.

## graphify

К проекту подключён [Graphify](https://github.com/Graphify-Labs/graphify) для ускорения навигации по коду и анализа связей и зависимостей при разработке. Локальный граф исходников `Source/` находится в `graphify-out/graph.json`.

- Поиск: `graphify query "<вопрос или символ>"`; связи: `graphify explain "<символ>"` или `graphify path "<A>" "<B>"`. В Claude Code доступен `/graphify`.
- Обновление графа после изменений: `graphify extract Source --code-only --out .` из корня проекта (локально, без API). Граф — вспомогательный инструмент; выводы сверять с актуальным кодом и решениями в `Docs/`.

Пути в графе отсчитываются от `Source/`. Разбор C++ частичный (Graphify предупредил о 14 файлах); граф не гарантирует полноту связей.
